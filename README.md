# WordPress Last Login

Показывает, когда и откуда каждый пользователь входил на сайт: в списке
пользователей появляются две колонки — дата последнего входа и IP-адрес, — а
список можно сортировать по времени входа.

Версия 1.3.3. Требуется WordPress 7.0+, PHP 8.0+.

## Установка

1. Скопировать каталог `WordPress-last-login` в `wp-content/plugins/`.
2. Активировать плагин в разделе «Плагины».

Настроек нет: плагин не создаёт своих опций и таблиц — только две записи в
метаданных пользователя (и кэш проверки обновлений в транзиентах). При
активации существующим пользователям проставляются нулевые значения в эти
ключи, чтобы сортировка работала для всех.

## Что появляется в интерфейсе

«Пользователи» → «Все пользователи»:

| Колонка | Что показывает |
|---|---|
| `Last Login` | дату последнего успешного входа в формате сайта; время — во всплывающей подсказке, в разметке — `<time datetime="…">` |
| `Last IP` | IP-адрес последнего входа ссылкой на `ipinfo.io` (открывается в новой вкладке) |

- Для пользователя, который ещё не входил, обе колонки показывают «Never.»
  (в русской локали — «Никогда.»).
- Клик по заголовку `Last Login` сортирует список по времени входа (как
  число, в обе стороны).
- Заголовки колонок переводятся: каталог переводов лежит в `lang/`
  (12 локалей и шаблон `.pot`); в русской локали это «Последний вход» и
  «IP-адрес». Формат даты можно переопределить фильтром `wpll_date_format`.

## Кто видит данные

По умолчанию — только пользователи с правом `manage_options`
(администраторы). Для остальных колонки не регистрируются вообще, поэтому в
разметке списка ни дат, ни IP нет. Проверка выполняется на `init`, после
загрузки плагируемых функций WordPress.

Право переопределяется фильтром `wpll_current_user_can`:

```php
// Разрешить также редакторам:
add_filter( 'wpll_current_user_can', function ( $can ) {
	return $can || current_user_can( 'edit_others_posts' );
} );

// Отключить для всех, включая администраторов:
add_filter( 'wpll_current_user_can', '__return_false' );
```

На мультисайте колонки добавляются и в список пользователей сети. Включая
фильтр, помните, что IP — персональные данные: право видеть их стоит выдавать
тем же людям, которым разрешено управлять пользователями.

## Что и как хранится

| Ключ метаданных пользователя | Значение |
|---|---|
| `wp-last-login` | Unix-время последнего успешного входа; `0` — входов не было |
| `wp-last-ip` | IP-адрес последнего входа; `0` — данных нет |

- Запись происходит при каждом входе: на `wp_login`, а при двухфакторной
  аутентификации — на `two_factor_user_authenticated` (плагины 2FA прерывают
  `wp_login` до прохождения второго фактора).
- При регистрации нового пользователя оба ключа создаются со значением `0`.
- При активации плагина нули проставляются только тем пользователям, у которых
  ключа нет: повторная активация или обновление не стирают уже записанную
  историю.
- Срок хранения не ограничен: значения перезаписываются при следующем входе,
  старые входы не хранятся. Отдельной политики хранения и автоматической
  очистки нет — если она нужна, удаляйте данные самостоятельно или
  деинсталлируйте плагин.
- Деинсталляция (`uninstall.php`) удаляет оба ключа у всех пользователей,
  на мультисайте — на каждом сайте сети, а также кэш проверки обновлений.
  Деактивация плагина данные не удаляет.

## Откуда берётся IP-адрес

По умолчанию записывается `REMOTE_ADDR` — адрес, с которого пришло соединение.

Заголовки `X-Real-IP` и `X-Forwarded-For` учитываются только тогда, когда
запрос пришёл от доверенного прокси: это адрес из локальной сети, loopback или
reserved-диапазона (обычный nginx на том же хосте или в той же сети), либо
адрес, явно перечисленный в фильтре `wpll_trusted_proxies`. Запрос, пришедший
напрямую с публичного адреса, записывается этим адресом, а его заголовки
игнорируются: иначе любой посетитель мог бы подставить в журнал чужой IP.

Для доверенного прокси порядок такой: `X-Real-IP`, затем последний элемент
`X-Forwarded-For` (его дописывает наш прокси при
`$proxy_add_x_forwarded_for`), затем `REMOTE_ADDR`. Значение проверяется
`filter_var( …, FILTER_VALIDATE_IP )`, поддерживаются IPv4 и IPv6; если ничего
корректного нет, IP не записывается.

Если прокси имеет публичный адрес (балансировщик хостинга, CDN), его нужно
указать явно, иначе в колонке будет адрес прокси:

```php
add_filter( 'wpll_trusted_proxies', function ( $proxies ) {
	$proxies[] = '203.0.113.10';
	return $proxies;
} );
```

## Обновления

Плагин обновляется штатным механизмом WordPress из репозитория
[Gnoztis/WordPress-last-login](https://github.com/Gnoztis/WordPress-last-login):
берётся **максимальная** версия из GitHub Release и тегов (`vX.Y.Z` и `X.Y.Z`
равнозначны), архив — zip-ассет или zipball победившего источника.
Предрелизы (`-beta`) и четырёхчастные версии (`1.2.3.4`) не принимаются,
поэтому достаточно поставить тег — создавать релиз не обязательно.

Проверка кэшируется на 6 часов, неудачная повторяется через 15 минут. Если
проверка не удалась, в строке плагина и в уведомлении на странице «Плагины»
показывается причина, например «проверка не удалась: 403 (лимит GitHub API)»,
и подсказка, что делать. Кнопка «Проверить обновления» сбрасывает кэш, снимает
бэкофф и запрашивает GitHub заново (в том числе после 403). Пакет принимается
только по `https` и только с доменов GitHub.

Ключ записи в списке обновлений — фактический `plugin_basename()` главного
файла, поэтому обновление работает из любого каталога (`WordPress-last-login/`,
`WordPress-last-login-main/` и т. п.): распакованный архив переименовывается в
имя установленного каталога.

### Токен GitHub (необязательно)

Без токена GitHub разрешает **60 анонимных запросов в час на IP-адрес**, а
каждая проверка обновлений делает два запроса — релиз и список тегов. Если с
одного IP проверяются несколько сайтов или плагинов с обновлением из GitHub,
квота заканчивается, и проверка отвечает 403 — в админке это выглядит как
«проверка не удалась: 403 (лимит GitHub API)».

Токен поднимает лимит до **5000 запросов в час**:

```php
// wp-config.php
define( 'WPLL_GITHUB_TOKEN', 'github_pat_…' );
```

или фильтром, например из переменной окружения:

```php
add_filter( 'wpll_github_token', fn() => getenv( 'WPLL_TOKEN' ) );
```

Нужен fine-grained personal access token с доступом только к репозиторию
`Gnoztis/WordPress-last-login` и правом **Contents: Read** — для публичного
репозитория этого достаточно. Токен уходит только на домены GitHub и только
для этого репозитория (запросы к API — на `api.github.com`, скачивание архива —
на `codeload.github.com` или подписанный хост ассетов), в интерфейсе он не
выводится: состояние видно лишь как «настроен / не настроен».

Без токена плагин работает, но проверка может упираться в лимит GitHub.

## Ограничения и персональные данные

- IP-адрес — персональные данные. Плагин не шифрует их и не маскирует:
  значение лежит в таблице метаданных пользователей открытым текстом.
- История входов не ограничена по сроку и не удаляется автоматически;
  единственный способ удалить всё сразу — деинсталляция плагина.
- Ссылка в колонке `Last IP` открывает `ipinfo.io`: при клике IP уходит
  стороннему сервису. Ссылка открывается в новой вкладке и без referrer.
- IP за прокси определяется эвристикой (см. выше). Если прокси не виден как
  локальный, без записи в `wpll_trusted_proxies` в колонке будет адрес прокси.
- Сортировка по последнему входу опирается на ключ метаданных: пользователь
  без этого ключа в отсортированный список не попадает. Ключ создаётся при
  активации плагина и при регистрации, поэтому на практике пропуск возможен
  только для записей, вставленных в базу в обход WordPress.
- На мультисайте метаданные пользователя хранятся в таблице каждого сайта:
  вход на одном сайте не виден в списке другого.
